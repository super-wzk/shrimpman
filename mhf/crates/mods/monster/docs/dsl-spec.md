# 怪物 AI DSL 规范

> 本文负责文本形态与编译规则，是 [`src/ai/dsl/`](../src/ai/dsl/) 的实现依据；第 11
> 节列的是尚未确证、编译器会显式拒绝的部分。原生事实以
> [`opcode-catalog.md`](opcode-catalog.md)、[`runtime-fields.md`](runtime-fields.md)
> 和 `opcodes-*.json` 为准。

## 1. 定位

一个文件描述一个物种的怪物 AI 图，形态是**基座 + 覆盖**：`base native;` 表示
在客户端原生图上覆盖，省略就是空基座。声明过的条目覆盖基座，没声明的条目
沿用基座内容——这条规则在两种基座下是同一句话，区别只在"基座内容"从哪来：
空基座没有原生条目，未声明的槽就是空槽；`base native;` 的编译产物在整图上记
一条"未声明槽沿用原生"，由安装方在**真正要替换的那个原生块**上解析（第 8 节）。
设计目标按优先级排列：

1. **可读优先。** 语句使用领域词；客户端自己已经打印出来的字面名字直接沿用
   （`kehai_end` 不译成 `alert_end`，`area_end` 不译成 `area_finish`），因为
   换个说法只会凭空多出一层词汇。
2. **布局不可见。** 作者只写名字和槽位编号，descriptor、槽位地址、事件 mask
   全部由编译器持有。原生布局是**固定**的而不是可推导的，所以这些知识属于
   编译器，不属于作者输入。
3. **无损，且不靠猜。** 能写出来的必须能和原生字节一一对应；还没搞懂的字节用
   `native(...)` 显式标注，不允许伪装成有语义的指令。没写出来的部分一律来自
   基座，不做任何推断。
4. **每类一个形式。** 状态机控制用关键字：`transition <state>;`、`restart;`、
   `repeat <n> { … }`；映射原生命令的用调用形式：`name(args);`。不提供括号
   可选之类的第二种写法，判别依据仍然放在名字解析规则上（见第 6 节）。

不做向后兼容：格式尚未发布，`mhf_ai 1;` 的作用只是将来变更时明确报错，
而不是承诺兼容。

### 术语分层

四层词汇在本文档里含义固定，不要混用：

| 层 | 写法 | 含义 | 例子 |
| --- | --- | --- | --- |
| 流程位置 | `states` 块成员 | 脚本当前在哪，只有一个活动 | `idle`、`combat` |
| 流程控制 | `transition <state>;`、`restart;`、`repeat <n> { … }` | 移动状态机的位置，或重复一段体 | `transition combat;` |
| 输入（只读） | 带 `self.` 限定 | 读本记录的原生字段，或引用门的判定结果 | `self.hate[3]`、`self.distance_to_reference()` |
| 指令 | 不带点的 `name(args);` | 会写内存或移动游标的原生命令 | `slash(0)`、`stop()` |

配套规则：

- **`.` 恒等于只读。** 带副作用的操作一律是顶层语句，不放进 `self.` 下——这样
  审一段 AI 时，"哪句会改状态"能一眼扫出来。
- **关键字不带括号。** `transition combat;`、`restart;` 是语句，`repeat <n> { … }`
  是块；`name(args);` 这种调用形式只留给映射原生命令的名字。
- 字段用下标取值（`self.hate[3]`），门查询用括号（`self.distance_to_reference()`），
  且查询只能出现在 `if` 条件里：原生没有"函数"，门读字段、比较、再决定跳过
  哪一段体，所以查询不能赋值、不能复用、不能组合（没有通用的与/或门，只有
  "一个量对一组常量"的列表形式；复合条件靠嵌套 `if`）。
- **输入层只有 `self.`。** 只读量都是本记录的字段或门判定结果，不引入指向
  另一条记录的限定形式。
- **当前目标不作为读量暴露。** 原生记录里的目标字段（`+2612`/`+1826`）是
  **域内下标**，解析依赖已提交的命令 kind；已有的原生读取都由解释器内部完成，
  没有确证的门或指令能让脚本把它当通用下标或比较量使用。
- 玩家域里，仇恨数据不在目标身上，而在怪物自己身上：`self.hate[i]` 即
  `+2688 + 2*i`，`+2687` 是每槽一个 bit 的可用标志，`+2788 + 4*i`、
  `+2824 + 4*i`、`+2740 + 4*i` 也是按同一下标索引的表。读这些 per-target 表
  用常量下标（`self.hate[2]`）。`FF F7` 的 `NOT_FOUND_PL` 只描述这条玩家域
  路径。
- 原生侧另有一处同名：`+2659` 在记录里叫 "script state"（运行 / 已推进 /
  停止）。它与 `states` 块不是一回事——`states` 对应的是 `+2576` 那张主表的
  下标，而 `+2659` 是脚本运行状态。本文档里 `states` 一律指流程位置。

## 2. 词法

| 元素 | 形式 |
| --- | --- |
| 注释 | `//` 到行尾 |
| 关键字 | 头部 `mhf_ai`、`species`、`base`；块内 `transition`、`restart`、`repeat`；都不带括号，见第 5、6 节 |
| 标识符 | 字母或 `_` 开头，后续为字母、数字、`_`、`-` |
| 数字 | 十进制，或 `0x` 前缀十六进制；字节范围 0..255 |
| 语句 | 以 `;` 结尾 |
| 块 | `{` 到 `}`，块内条目一行一条，不需要逗号 |

## 3. 文件结构

```text
mhf_ai 1;
species 6;
base native;

actions { ... }
events  { ... }
states  { ... }
```

头部三行里 `mhf_ai` 和 `species` 必写，`base` 可选：省略表示空基座，写
`native` 表示在客户端原生图上覆盖（第 8 节）。声明块顺序无关，formatter 负责
排出规范顺序。一个文件对应一个物种，`species` 决定原生侧选择哪一格
（`0x10860360`）；地图不进头部，同一物种不同地图写成不同文件，由安装层
按 `(map, species)` 路由（第 8.2 节）。

## 4. 声明块

### 4.1 `actions` —— 原生 action 词汇表

```text
actions {
    slash = [3:6];
    bash  = [4:1];
}
```

`[group:id]` 是原生 action 表的坐标，两个数都在 0..255。调用处给参数：
`slash(0)` 编码成 `05 03 06 00`。

别名是可选糖：也可以匿名调用（见第 5 节）。无论用不用别名，`actions` 块是
本文件 action 名字的**闭集**，这是第 6 节判别规则的基础。

### 4.2 `events` —— 原生事件槽

```text
events {
    roar = 0 {
        slash(0);
        kehai_end();
    }

    hit = 2 {
        bash(1);
    }
}
```

槽位编号 `0..6` 是原生固定编号，编译器持有它到事件 mask 和 `main` 表下标的
映射（第 9 节），作者不需要写 mask 或地址。

别名可省：直接写槽位号，例如 `0 { ... }`。事件体就是该 lane 的脚本；块尾的
收尾命令由编译器补，但事件 lane（`0x40`/`0x80`）的收尾尚未确证，所以现在
留空（第 7 节、第 11.3 条）。没有响应的事件不写：空基座下就是空槽，
`base native;` 下"不写"等于沿用原生脚本，要清掉某个原生槽就写裸条目
`roar = 0;`。

槽里存的是"指针格"而不是脚本本身：原生分派读 `cell[0]`（第 9 节）。声明了
体的事件在编译产物里只占一格——`cell[0]` 指向本文件的脚本；解析时把这一格
叠到原生格子上，`cell[1..]` 沿用原生条目，原生没有格子时才新建一格。没声明的
槽不进编译产物，整个指针沿用原生条目。

### 4.3 `states` —— 状态

```text
states {
    idle {
        slash(0);
        transition combat;
    }

    combat {
        bash(1);
        transition idle;
    }
}
```

带体的是完整状态；不带体的裸条目（`roam;`）表示该槽位在本文件里没有脚本，
编译成空槽。

下标按顺序给：第一条是 0，之后每条 +1；写 `= N` 就把游标设到 N，后续继续
递增（和 C 枚举一样）。

```text
states {
    idle   { slash(0); transition combat; }
    combat = 3 { bash(1); transition idle; }
    flee   { stop(); }
}
```

上面三个条目占下标 0、3、4。**声明过的下标覆盖基座，没声明的下标沿用基座
内容**：空基座下是空槽（上例的结果是 `[idle, NULL, NULL, combat, flee]`），
`base native;` 下解析时按同一下标取原生脚本。编译产物是"下标 → 脚本"的映射，
不带长度：声明过的下标就是它的全部内容，表尾和空洞都由安装层在原生表上补齐
（第 8.1 节）。状态表落在 `main[0]`，解释器能寻址的下标范围是 0..255。

`transition <state>;` 只在这个块里有意义（见第 7 节），目标必须是本文件声明的
状态名，编码用该状态锚定的下标。

## 5. 指令

状态机控制是关键字，不带括号；原生命令统一写成 `name(args);`。名字来自保留
表或本文件的 `actions` 块。

| 形态 | 示例 | 原生编码 | 说明 |
| --- | --- | --- | --- |
| 状态转移 | `transition combat;` | `07 <index>` | 写 `+2576`，把当前游标切到 `main[0][index]`；只在 `states` 块里合法 |
| 回到状态表开头 | `restart;` | `04` | 把 `+2576` 清 0 并装入 `main[0][0]`；不清 lane 掩码、delay、触发锁存；只在 `states` 块里合法 |
| action 别名调用 | `slash(0);` | `05 03 06 00` | 参数是 action 参数 |
| 匿名 action 调用 | `action[3:6](0);` | `05 03 06 00` | 自带 `action` 前缀，不会与别的名字混 |
| 表尾返回 | `resume();` | `ff 01` / `ff 02` / `ff 03` | 回到当前表保存的游标；字节由块所属表类型决定，还没有块持有游标，编译器当前拒绝（第 11.2 条） |
| 结束运行 | `stop();` | `68` | 置 `+2659`=2、`+2622`=1 并走重启收尾；与 119 个 default 字节等价 |
| 清目标 | `clear_target();` | `1e` | 清选择 id、游标、目标下标及相关上下文字节 |
| 等待 | `wait(n);` | `48` + `n` | 写入 `+3228`（延迟 tick）；消费方未确证，名字暂定 |
| 空指令 | `nop();` | `92` / `93` | 只消耗 opcode 字节，占位用 |
| 通道收尾 | `kehai_end();` | `ff fd` | 作者可写的路由/通道收尾家族，见第 6 节 |
| 原生转义 | `native(0xff, 0xfd);` | 原样字节 | 还没搞懂的命令走这里 |

**块形式 `repeat`。** `0x24`/`0x25` 是解释器里唯一的循环机器，做成块而不是
指令：

```text
states {
    idle {
        repeat 3 {
            slash(0);
        }
        transition combat;
    }
}
```

选择子 0 存重复次数与体游标，选择子 1 递减计数并回跳，`0x25` 负责复位。
计数直接写在关键字后面并且不带括号——块形式的关键字同样属于流程控制层，
`repeat(3) { … }` 是硬错误。

**为什么只有这几条。** 137 条已分派 opcode 里绝大多数是条件门和字段簿记，
它们是数据生成器喂给解释器的输出，手写等于手写编译器 IR。命名判据是三条
同时成立：决定"下一步去哪"或作者要主动做的事情、语义已验证到能起名、作用
无法用别的已命名指令加数据表达。三条缺一条就留 `native(...)`。

**还没到命名阶段的。** `0xff` 的 `0x01`/`0x02`/`0x03` 与 `0x81`/`0x82` 是
分层游标的进入与返回，最终应该长成 `enter(...)` 与 `resume()` 一对，但形态
取决于 contents / sub-contents 块的设计（第 11 节）。`0x11`/`0x12`/`0x13`/
`0x45`/`0x52`/`0x53`/`0x5e`/`0x5f`/`0x7e` 九个都在"选一个 lane 或目标"，
目前分不清彼此差别，起九个近义名字比留地址更糟。

**`resume()` 的确切字节由块决定**：contents 表 `ff 01`、sub-contents 表
`ff 02`、route 表 `ff 03`。也就是说它只有在这些表类型在 DSL 里有对应块之后
才能编译；目前只有状态表和事件体有块，所以示例里没有用它。

**`native(...)` 是唯一的裸值形式。** 它的存在本身就是在说"这条还没搞懂"。
使用它时编译器应给出提示，提示内容直接用 opcode 记录里的条目（如果该字节
已分派但未命名）。

## 6. 名字解析与冲突

解析顺序固定：

1. 查流程控制关键字（`transition`、`restart`、`repeat`）；
2. 查保留命令表（`resume`、`kehai_end`、`area_end` …）；
3. 查本文件 `actions` 块声明的别名；
4. 都没有 → 报错：未声明的 action，或未知名字。

`transition` 后面必须跟一个本文件声明的状态名；`restart` 不带操作数；`repeat`
后面必须跟一个字面计数（0..255）再跟块。三者都没有括号形式：
`transition(combat);`、`restart();`、`repeat(3) { … }` 都是硬错误，不提供两种
写法。计数是字面量而不是状态名，因为它直接落进 `+2623`，不对应任何表下标。

因为 `actions` 是闭集，"`slash` 是 action 吗"这个问题在同一个文件里就能
回答，不需要靠语法形态判断。硬检查：

- `actions { kehai_end = [3:6]; }` → 硬错误：与保留命令名冲突。**不允许**
  别名静默覆盖内置行为；`transition`、`restart`、`repeat` 同样不能作为
  action 别名。
- 调用了没声明的名字 → 硬错误，而不是当成未知命令或十六进制字节。
- 保留名分三层，都只收已有证据确认的名字：
  - **流程控制关键字**：`transition`、`restart`、`repeat`。`transition` 后接
    状态名，`restart` 无操作数，`repeat` 后接字面计数与块。
  - **作者可写命令**：`stop`、`clear_target`、`wait`（暂定）、`nop`、
    `resume`，以及路由/通道收尾家族 `kehai_end`、`area_end`、
    `route_move_end`、`find_end`、`find_ng_end`、`no_floor_end`。
  - **框架专用**：`reset`（`ff 00`）、`unko_end`（`ff f5`）这类由解释器
    自己发的命令。它们会清 lane 掩码并把主表下标、stage、游标一起拉回原点，
    作者手写几乎总是错的，所以进了词表但要报错。
  - 三层都拒绝同名的 action 别名。

`restart` 与 `reset` 不是一回事，别混：`restart`（`0x04`）把 `+2576` 清 0
并装入 `main[0][0]`，也就是回到状态表开头；它不清 lane 掩码、delay 和触发
锁存。`reset`（`ff 00`）走重启收尾 `0x10860430`，连 lane 掩码、delay、触发
锁存一起清掉。作者要"结束整个 AI 运行"用的是 `stop()`。

靠标点区分指令种类是有害的：`kehai_end;` 与 `kehai_end();` 只差一个标点却是
不同语义，手滑就会静默改义；闭集解析的手滑是硬错误。

## 7. 作用域与检查

编译器能**确定**检查的规则：

| 规则 | 检查内容 |
| --- | --- |
| `transition <state>;` 只在 `states` 块 | `07` 只改当前 lane 游标与 `+2576`，不写基 lane 的保存游标（`+2548`/`+2588`）；写在 `events` 里是错误 |
| `restart;` 只在 `states` 块 | `04` 清 `+2576` 并装入 `main[0][0]`，操作的是状态表入口，同样只对基 lane 成立 |
| `repeat <n> { … }` 的形式 | 计数是字面数字（0..255），写在关键字后；`repeat(3) { … }` 是硬错误 |
| `repeat` 单层，不可嵌套 | 计数器只有一个字段（`+2623`），`0x25` 会直接把它清掉 |
| 保留名 / 未声明名 | 见第 6 节 |
| 操作数范围 | 字节 0..255；`transition` 的目标必须是本文件声明的状态 |
| 块尾补全 | 作者不写表尾命令，编译器按块的 lane 归属补；事件 lane 的收尾尚未确证，先留空（第 11.3 条） |
| 条目下标 | 同一块内不重复，范围 0..255；写 `= N` 之后的条目继续递增 |
| 未声明的条目 | 沿用基座内容：空基座是空槽，`base native;` 解析时取原生脚本（第 8 节） |
| 裸条目 | 裸状态条目就是把该下标编译成空槽，用来清掉基座里的条目 |
| 原生基座绑定构建 | 覆盖只在固定构建下有意义；解析校验的是 `species` 与图结构，构建身份由安装层保证（第 11.10 条） |

**`events` 里不能切换状态。** 原生 `0x07` 只改当前分派游标 `+2652` 和全局主表
下标 `+2576`，不写任何 lane 的保存游标（`+2548`/`+2588`/`+2596`/`+2604`）；
事件 lane 里执行它只会让这条事件 lane 跳进 `main[0][index]` 继续执行，基 lane
下次仍从自己的保存游标恢复。事件想影响基状态，走显式共享量：事件写字段/标志
或发命令，由基状态的门读取后自行 `transition <state>;`。

**lane 活动性是运行时属性，静态检查不了。** 例如 `kehai_end()` 的目标是 lane
`0x10`，它能成立的前提是那条 lane 此刻处于活动状态——这取决于运行时的 lane
掩码，不是文件里能证明的。所以编译器对跨 lane 命令只能给提示，不能证伪。
是否要求跨 lane 操作显式标注，是待定项（第 11 节）。

块尾由编译器补的理由：每条 lane 的收尾命令不同，而块的 lane 归属在文件里
已经写明。让作者手写常量等于把编译器知识抄进用户输入。

## 8. 基座与合并

`base native;` 让本文件在客户端原生图上做覆盖；没有它，基座是空的。两种情形
共用一条规则：**声明过的条目覆盖基座，没声明的条目沿用基座内容**。区别在
"基座内容"什么时候进来：

- 空基座：编译器直接产出完整图，未声明的槽就是空槽。
- `base native;`：编译器只产出声明过的条目，并在整图上标一条"未声明下标沿用
  原生"。原生表和脚本不进编译产物，也不需要在编译期读取；绑定层从 actor 刚
  选中的那个原生块上读一段窗口，按同一下标把声明叠上去，再发布私有块
  （`src/ai/bind.rs`）。

### 8.1 状态表怎么合并、窗口谁来定

`states` 落在 `main[0]`，下标是 `+2576`，类型是 **u8**（`0x10860340` 里
`movzx eax, byte ptr [ecx+0A10h]` → `mov eax, [edx+eax*4]`），所以解释器能
寻址的状态下标只有 0..255。这个宽度只是下标宽度，不是表长：编译器只写声明过
的下标（键值对），窗口留给写出层。

**为什么是窗口而不是"读到表尾"**：原生状态表没有长度字段，也没有终止符。

| 现象 | 例子 |
| --- | --- |
| 表中间允许 NULL 空洞 | map 0 species 2 的表在下标 57 是 `0`，下标 58 起仍然是脚本指针 |
| 表尾没有终止符 | map 0 species 9 的表读 80 项都没有出现 `0`，之后紧邻的是非指针数据 |
| "第一个 0 之后全零"不是规律 | map 0..7 × species 0..131 共 1056 张表里只有 201 张满足，另外 855 张不满足 |

所以绑定层读窗口不是猜测：解释器对任意可达下标读到的就是同一批数据。窗口把
表后紧邻的数据一并纳入，但只有下标落到真实表外时才可能读到，而那时原生侧读到
的也是同一批数据。取多大由读者能形成的最大下标决定，绑定层按窗口大小分档：

| 位置 | 窗口 | 依据 |
| --- | --- | --- |
| descriptor | 15 个固定槽 + 尾 0..255，共 271 字 | 尾部按内容下标访问：`0x10866F97` 读 `[descriptor + 0x3C + index*4]` |
| 状态表（`main[0]`） | 0..255 | 两个读者都先 `movzx` 一个字节再索引 |
| 路由槽（mask `0x02`） | 0..255 | `route_ptr_set` 按 act 取 `[cell + act*4]` |
| 其余六个事件格 | 声明写到的最大下标 | 派发器只读 `cell[0]` |

**窗口归写出层，不归图。** `Program` 里的每个表只是"下标 → 节点"的映射，没有
长度字段，缺席下标的意思是整图级的标记；图本身没有可对齐的窗口，窗口是绑定层
的事。声明里出现窗口之外的下标会被拒绝，而不是按猜出来的窗口改写——那会动到
客户端用另一种下标宽度读的数据（第 11.1 条）。

**未声明的下标什么时候取到指针。** 原生表不进编译产物：`Program` 里只有声明过
的下标，外加一个"缺席下标沿用原生"的基座标记。绑定层把活块整窗拷一份：未声明
的下标保持原值，声明过的下标覆盖它们，声明为空的条目写 0（丢掉指针，`root[0]`
不允许清）。所以编译产物不绑定某一份原生数据，代价是叠加必须发生在活块存在的
时候。

**谁会写下标。** 扫过 `.text` 里全部 `[reg+0A10h]` 引用后，写入点只有四处：

| 地址 | 写入 | 值 |
| --- | --- | --- |
| `0x10860360` 记录初始化/选物种 | `mov [esi+0A10h], bx` | `ebx = 0` |
| `0x10860430` 回原点收尾（`stop`/`reset` 走它） | `mov [eax+0A10h], dl` | `edx = 0`，随后把 `main[0][0]` 装进游标 |
| `0x108675A0` `UNKO_END` 族 lane 收尾（9 处） | `mov byte ptr [esi+0A10h], 0` | 0 |
| `0x1086978E` / `0x108697CF` 解释器 handler | `mov [esi+0A10h], bl` / `, al` | 脚本的 `04` / `07` 操作数 |

非脚本代码只会把它写回 0，唯一的非零来源是脚本里的 `0x07`。所以空基座不需要
预留 0..255：可达下标就是 `{0} ∪ {本文件 transition 的目标}`，图里只写这些
下标，窗口留给写出层。0..255 是下标宽度决定的可寻址范围（`0x10860340` 的
`movzx` 之后是 `[main + eax*4]`），不是布局要求。

`events` 不需要这套机制：槽位是固定的 7 个编号，槽位格就在物种块里，覆盖直接
写那一格。`main[6]`（地面区域移动脚本表）指向的是另一张表，索引来自活着的
记录而不是本文件的声明（`+0A37`），所以覆盖它要整窗处理，不能按可达下标裁剪；
下标宽度已确认为 u8（`0x1086208A` 的 `movzx`），但用什么块表达还是第 11.1 条。

槽位 6（mask `0x02`，`main[8]`）是同一件事的另一半：那张表的 `cell[0]` 就是
这个事件的脚本，其余项归 `route_ptr_set` 按 act 取用（`0x108604C0` 的
`movzx edx, dl` → `[cell + act*4]`）。所以绑定层对它保留整张 u8 窗口，声明
只替换 `cell[0]`；裸条目也只清 `cell[0]` 而不清整格——清整格会连带删掉所有
act 的路由脚本。另外六个槽位没有第二读者，窗口就是声明自身的长度。

### 8.2 作用域

`species` 决定查哪一格：`em+2544 = off_11A4BD68[map][species]`（`0x10860360`
里 `mov ecx, [eax+34h]`（MapID） → `mov eax, ds:off_11A4BD68[ecx*4]` →
`mov ecx, [eax+edx*4]` → `mov [esi+9F0h], ecx`）。记录里的 `+9F0` 就是这个
物种块指针，而**物种块的第一个 dword 是状态表指针**：`0x108603B6` 起
`mov edx, [esi+9F0h]` → `mov eax, [edx]` → `mov eax, [eax+ecx*4]`，也就是
`main[index]`。物种块固定 132 项（`0x210` 字节），并且在多个 map 之间、多个
species 之间共享（map 0 与 map 1 指向同一块；同一个 map 里 species 0 与 1 也
指向同一块），所以覆盖必须先复制物种块再改，不能就地写原生数据。

行下标就是 MapID：`0x10AA5D19` 把任务的 MapID 写进 `+0x34`，没有任务时
`0x10AA5F9D` 写 2。因此**同一物种在不同地图上可以有不同的 AI**，而地图不进
DSL 头部：同一物种同一地图一个文件，安装层按 `(map, species)` 选择要解析并
替换的那一格（目录布局与查找规则见 8.3 节）；行是共享的，替换前必须复制。
地图 33、34、36–43、45、46、70 的行是空的，那些地图上没有可继承的原生条目。

species > 0x83 的怪不走这张表（同一个分支里改走 `sub_1086E100(map, species)`
的 per-species switch），这套覆盖机制对它们不生效。

### 8.3 数据目录与加载

数据根是游戏目录下的 `dat/monster-ai/`（会话期进程的当前目录就是游戏目录，
会话结束才还原）。文件名承担路由，DSL 头部不写地图：

```text
dat/monster-ai/
    6.mhai          // 物种 6 的全地图默认
    0/
        6.mhai      // map 0 的覆盖，优先于默认
    2/
        131.mhai
```

一个文件描述一个 `(map, species)` 的覆盖：目录名是 `off_11A4BD68[map][species]`
的行号（MapID），文件名是同一行的列号（species）。两侧都写十进制、不补零，
扩展名只有一个 `.mhai`（小写），文件里的 `species N;` 必须等于文件名。

加载按需发生：只有真的要取用某一格时才按两个 id 拼路径打开，依次尝试

1. `dat/monster-ai/<map>/<species>.mhai`；
2. `dat/monster-ai/<species>.mhai`（全地图默认）；
3. 两次都不存在，这一格保持原生不动。

加载层不枚举目录、不查询属性。dat-redirect 只重定向文件打开，目录枚举和属性
查询看到的始终是游戏自带的 `dat` 树；而这一格的键本来就在原生表里，不需要
扫描来发现。覆盖根（dat-redirect 的 `root`）镜像同一相对路径，所以这两次
打开自动经过它，加载层不需要知道 root 在哪。

错误语义分层：`NotFound` 落到下一级，是正常控制流；其它 IO 失败要记录并跳过
这一格，不能当成"没有文件"继续往下走；打开成功而解析失败是这一格的硬错误，
不回落到原生——文件存在就意味着作者要覆盖。活着的记录上只有"原生"和"私有块"
两种状态，所以硬错误的表现是：这一格报错、actor 仍跑原生、错误不进缓存，之后
每次取用都重试，改好文件后不必重开会话；"没有文件"才进缓存。

默认文件里写 `base native;` 时，是在每个格子上各自解析的：同一份文件装到
map 0 和 map 2，各继承各自的原生条目。地图 33、34、36–43、45、46、70 的行是
空的，没有基座可继承，`base native;` 的默认层在那里跳过并提示；species >
0x83 不适用。数据根里只有文本，编译产物不落盘，构建身份由安装层校验
（第 11.10 条）。非规范拼写（`007/6.mhai`、`6.MHAI`）运行期不会被命中，
这类检查属于管理器。

加载发生在记录初始化（`0x10860360`）之后、原生游标已经建好之时：安装层在该
调用返回后把 `+9F0` 换成私有块，并用私有状态表和 `+A10` 重算 `+9F4`/`+A5C`
（第 11.4 条）。这不影响这里的路径与查找规则。

## 9. 编译器持有的原生布局

作者看不到这些位置，编译器必须持有它们：

| 位置 | 含义 | 证据 |
| --- | --- | --- |
| `main[0][0..255]` | 状态表，由 `+2576` 索引；编译产物只带声明过的下标，窗口由绑定层写出（第 8.1 节） | `0x10860340`（`em_cmd_top`） |
| `main[3]` | 事件槽，mask `0x10` | `0x108605F3`（`[edx+0Ch]`，游标存 `+0A24`） |
| `main[4]` | 事件槽，mask `0x20` | `0x108605AB`（`[ecx+10h]`，游标存 `+0A2C`） |
| `main[8]` | 事件槽 mask `0x02`，同时是 `route_ptr_set` 按 act 索引的数组 | `0x108604C0`（`[ecx+8]`）、`0x108606CB`（`[edx+20h]`，游标存 `+0A4C`） |
| `main[10]` | 事件槽，mask `0x04` | `0x10860683`（`[ecx+28h]`，游标存 `+0A50`） |
| `main[11]` | 事件槽，mask `0x08` | `0x1086063B`（`[eax+2Ch]`，游标存 `+0A54`） |
| `main[13]` | 事件槽，mask `0x80` | `0x1086056B`（`[edx+34h]`） |
| `main[14]` | 事件槽，mask `0x40` | `0x1086052A`（`[eax+38h]`） |
| `main[6]` | 地面区域移动（`em_cmd_area_route_move`）脚本表，按 `+0A37` 的字节索引 | `0x10862091`（取块）、`0x1086209D`（`[eax+18h]`）、`0x108620A0`（`[ecx+edx*4]`） |

DSL 槽位编号到事件 mask 的固定映射（来源：`src/ai/control.rs` 里的 `EVENT_SLOTS`，
该表按原生 descriptor 的 mask 顺序建立）：

| DSL 槽位 | 0 | 1 | 2 | 3 | 4 | 5 | 6 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 事件 mask | `0x40` | `0x80` | `0x20` | `0x10` | `0x08` | `0x04` | `0x02` |
| `main` 下标 | 14 | 13 | 4 | 3 | 11 | 10 | 8 |

运行时 lane 掩码（`+3288`）是这些槽位的并发模型，也是"状态只有一个、事件体
却能同时跑"的原因：

| 位 | 含义 |
| --- | --- |
| `0x01` | 基 lane，游标 `+2588`，跑 `states` |
| `0x02` / `0x04` / `0x08` | 命令 lane，收尾见 `ff fa` / `ff f9` / `ff f8` |
| `0x10` | 気配 lane，游标 `+2596`，收尾 `ff fd`（`kehai_end`） |
| `0x20` | 游标 `+2604` |
| `0x40` / `0x80` | 两条互斥事件 lane |

记录里 `+2596` 那条把 lane `0x10` 写成 "event lane"，与 `+3288` 这条（事件
lane 只有 `0x40`/`0x80` 两条）不一致；`KEHAI_END` 清 bit `0x10` 这一点支持把
`0x10` 当作気配 lane，本条按后者写。

## 10. 示例

```text
mhf_ai 1;
species 6;

actions {
    slash = [3:6];
    bash  = [4:1];
}

events {
    roar = 0 {
        slash(0);
        kehai_end();
    }

    hit = 2 {
        bash(1);
    }
}

states {
    idle {
        slash(0);
        transition combat;
    }

    combat {
        bash(1);
        transition idle;
    }
}
```

编译结果：

```text
main[0]  状态表 [idle, combat]
main[14] roar 槽（mask 0x40）
main[4]  hit  槽（mask 0x20）

idle   = 05 03 06 00         // slash(0)
         07 01               // transition combat，combat 是索引 1
combat = 05 04 01 01         // bash(1)
         07 00               // transition idle
roar   = 05 03 06 00
         ff fd               // kehai_end()
hit    = 05 04 01 01
         <编译器补本 lane 的收尾>
```

`hit` 的收尾留空是有意的：事件 lane（`0x40`/`0x80`）的收尾命令尚未确证，由
编译器按块的 lane 归属补，而不是让作者写个常量碰运气。`roar` 里的
`kehai_end()` 是显式跨 lane 操作：roar 属于 `0x40` 事件 lane，而
`kehai_end()` 结束的是 `0x10` 的気配 lane。

### 原生基座上的覆盖

```text
mhf_ai 1;
species 6;
base native;

events {
    roar = 0 {
        kehai_end();
    }
}

states {
    idle = 3 {
        slash(0);
        transition combat;
    }

    combat = 4 {
        bash(1);
        transition idle;
    }
}
```

编译结果：

```text
states    只带下标 3、4 两段脚本，其余下标由安装层补齐
main[14]  roar 只写 cell[0]，格子其余条目和另外六个事件槽都沿用原生
idle   = 05 03 06 00
         07 04               // transition combat，combat 被锚在下标 4
combat = 05 04 01 01
         07 03               // transition idle
```

新条目的下标由锚点决定，没写锚点的条目顺着前一条往后续；原生在别处的条目不动。
安装时安装层先在活块上读窗口，再把声明按同一下标叠上去：没声明的槽取原生
条目，`main[14]` 只换 `cell[0]`。所以这个文件不需要在编译期拿到原生数据。

## 11. 待定

1. 按 act 索引的路由脚本（`main[8][act]`）和地面区域移动脚本（`main[6]`，
   `+0A37` 索引）在 DSL 里怎么表达。两者都按固定下标取用（`0x108604C0`、
   `0x10862010`），下标宽度都已确认是 u8，索引来自活着的记录，覆盖要整窗
   复制而不是按 §8.1 的可达下标裁剪。事件的半边已经落地：槽位 6 只替换
   `cell[0]`，其余 act 沿用原生（第 8.1 节）；整张表本身还没有写法，绑定层
   对声明 `main[6]` 的文件报 `descriptor slot 6 has no binding window yet`
   （`src/ai/bind.rs`）。
2. contents / sub-contents / route 这三类表在 DSL 里怎么出现——`resume()` 的
   字节取决于它们。
3. 事件 lane（`0x40`/`0x80`）的收尾命令是什么。
4. 解析与安装的时机。安装点已经追到：`0x10860360` 是客户端里唯一写 `+9F0`
   （物种块）和 `+9F4`/`+A5C`（状态游标）的地方，唯一调用点是 `0x1086EB51`
   （`sub_1086EAD0`），返回后紧接着走 `0x10860430`。所以安装层在这一步返回后
   整体换成私有块，原生初始化照常跑完、覆盖随之上线（第 8.3 节）。
   没追到的部分：`main` 的槽位里有指向 BSS 的值（例如 species 6 的
   `main[2]`/`main[15]`），如果物种块本身会在运行期被原生改写，绑定层"每格
   首次取用时读一次活块并缓存"的副本就会落后；客户端换图或重建记录时会不会
   重新生成物种块也还没追（钩子每次都会重跑，但绑定缓存按 `(map, species)`
   命中，命中后沿用第一份副本）。
5. `wait` 的名字。`0x48` 写 `+3228`，但读这个字段的消费方还没追到；确证前
   `wait` 只算暂定名，也可能该按原生叫法改名。
6. `0x0f`/`0x10`/`0x16` 这套"设上下文 + 绑脚本表 + 选下一个变体"的机器怎么
   在 DSL 里出现。它对应原生 descriptor 里标注为 `content_variants` 的那类
   槽，倾向做成块而不是 `select_variant();` 这样的指令。
7. 跨 lane 操作是否需要显式标注。
8. 目标选择器及相关 lane 绑定的表达。当前目标暂不作为读量暴露（原生证据见
   `runtime-fields.md`）。仍需把
   `0x11`/`0x12`/`0x13`/`0x45`/`0x52`/`0x53`/`0x5e`/`0x5f`/`0x7e` 各自落到
   哪个域读清楚，再决定选择结果在 DSL 里是只由指令表达，还是需要单独的读取
   形式。若将来确证了原生读取路径并引入当前目标，名字沿用 `self.target`，
   不另造 `slot` 类名字。
9. `repeat` 的体标记与允许出现的块。计数（`+2623`）和体游标（`+2632`）都是
   记录级字段，两条 lane 同时跑 `repeat` 会互相覆盖；是否限定只在 `states`
   块内使用，要看原生数据里有没有事件体用 `repeat` 的情形。更硬的一条：
   handler `0x108628F0` 用 `sub_10860A10(..., '$', 2)` 扫 `24 02` 再跳过 3
   字节，而宽度例程 `0x10860730` 对选择子 0 只前进 3 字节、对选择子 1 前进
   2 字节，两者对体标记长度的口径不一致。原生数据里 165 处 `[24 00 …]` 又
   多数没有配对的 `24 02`，所以收尾序列尚未确证。**编译器拒绝生成 `repeat`**
   （解析与格式化照常）。
10. 构建身份的承载位置。`base native;` 的覆盖只在固定构建（README 里那枚
   `mhfo-hd.dll` SHA-256）下才有意义，但 `Program` 里没有承载构建身份的字段，
   所以解析只能校验 `species` 与图结构。要真正拒绝错配的活块，得先决定身份
   放在哪一层：`Program` 的字段、安装层的配置，还是解析入口的参数。

### 编译器的拒绝清单

以下输入语法上可读，编译期报错，报错即第 11 节里的待定项（不是 bug，也不
留给作者用 `native(...)` 绕过的隐式行为）：

| 输入 | 报错理由 |
| --- | --- |
| `repeat 3 { … }` | 第 11.9 条的体标记口径不一致 |
| `resume()` | 第 11.2 条：没有块持有对应表的游标，字节取决于块类型 |
| `reset()`、`unko_end()` | 第 6 节：解释器自己发的命令 |
| `self.…`、`if …` | 第 7 节：条件与只读量在语言里还没有落点 |

`native(...)` 不是拒绝，而是显式转义：编译器原样写入字节并给出一条提示，提示
内容说明首字节属于哪一类（已分派但未命名，或落到 switch default）。跨 lane 的
命令（例如事件体里的 `kehai_end()`）同样只提示不报错，因为 lane 活动性是运行时
属性（第 7 节）。
