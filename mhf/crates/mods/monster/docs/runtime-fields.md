# 怪物 AI 运行时字段

本文件记录固定 `mhfo-hd.dll`（镜像基址 `0x10000000`，SHA-256
`95c580195f4080d2e9582c8c9df36abeb280476e088b6366583c5f138da8f301`）里
解释器的 `this`/`a2`/`esi` 指针实际指向什么。它是逐 opcode 语义的支撑证据：
只有原生消费者证明了角色，操作数才会被赋予角色；只有发行版自己打印或存过的
名字，才会被当作游戏词汇使用。

## 名字是怎么恢复的

解释器对象是怪物（"em"）实体。下面的名字来自四类原生证据：

- 发行版仍传给空 logger `nullsub_2` 的调试标签字符串：
  `"T_KIND_AREA maji_next_stage_no:%d"`（`0x10869917`）、
  `"FIND_NG_END em->cmd_pl_target == NOT_FOUND_PL"`（`0x10867D41`）、
  `"KEHAI_END route_ptr_set( em, em->cmd_route_act )"`（`0x10867EFC`）、
  `"KEHAI_END cmd = em_cmd_top( em ) em_g_init_flag_set(em,EM_NET_CMD)"`
  （`0x10867F20`）、`"FIND_END Em_Mode_Chg( em, EM_MODE_ATTACK )"`（`0x10867EA1`）
  和 `"em_cmd_mind_ck MIND CKH:%d(%s) != NOW:%d"`（`0x1086218B`）；
- 这些打印使用的名字表：actor 类型名 `EM_EXC` 与 `KIND_EMY..KIND_NOT` 在
  `0x1199D870..0x1199D918`（指针数组在 `0x11A4BF74`，后面跟着 act-id 基数表
  `0x11A4BFB0`），命令名
  `EM_EXC/EM_VSD/EM_REV/EM_DEM/EM_DIE/EM_DMG/EM_ATK/EM_FLY/EM_MOV/EM_ACT`
  在 `0x1199D918..0x1199D960`；
- 物种名表 `EM_*` 在 `0x1199CE9C..`，结合 `0x10860360` 里的表选择
  `off_11A4BD68[map][*(em+3)]`，`map` 即 `dword_1E7FFF3C+0x34` 的任务 MapID；
- 游标 helper 实际走的表布局：`root[0]` 在 `0x10860340`、`root[2]` 在
  `0x108604C0`、`root[6]` 在 `0x10862010`（该函数还打印
  `"em_cmd_area_route_move"`，`0x1086208A` 起）。`main[N]` 一律指物种块的
  dword 下标，与 `root[N]` 相同；`root[2]` 是 descriptor 字节偏移 `+8`，
  `root[6]` 是 `[eax+18h]`（字节偏移 24）。`root[8]` 是诱饵事件槽。

下面的偏移是十进制字节偏移，默认从实体指针起，除非明确写了别的指针。

## 控制写入的消费者边界

### 0x0C / 0x0D 的选择子

`0x108611F0`（`0x0C`）和 `0x108612F0`（`0x0D`）操作同一批字段，
但这些字段有计数、请求闩、接管状态和物种专用状态等不同角色，不能合并为一个

| selector | 字段 | 执行条件与区别 |
| --- | --- | --- |
| 0 | 逐个处理 1..10 | 应用各分支自己的门控；不是单一字段 |
| 1 | `+2683` | 感知/闪光抑制计数，无物种门控 |
| 2 | `+2736` | 优先级 `0x50` 请求的已触发闩，不是其计时值 |
| 3 | `+3186` | 感知更新抑制计数，无物种门控 |
| 4 | `+2602` | 处理器接管状态；清除后继续执行，独立于返回 |
| 5 | `+1296` | 物种 7/50 且 `+2739 == 0` |
| 6 | `+1364` | 物种 15/45 且 `+2739 == 0` |
| 7 | `+1365` | 物种 15/45 且 `+2739 == 0` |
| 8 | `+1296` | 物种 55 且 `+2739 == 0` |
| 9 | `+1296` | 物种 58/72 且 `+2739 == 0` |
| 10 | `+2846` | 仅 `0x0D` 写 `0xFFFF`；`0x0C` 无动作 |

### 目标 kind 与坐标来源

`0x31` 只设置 kind 8。后续 `0x108538B0` case 8 从
`+2864/+2868/+2872` 取得 `0x10856A10` 已扫描的缓存点；指令本身不会重新扫描，
缓存点的物件类别也未证明，不能命名为 home 或直接等同于 `0x2D` 的地面物件。

`0x49`（`0x10864640`）使用当前玩家目标 `+2612`：无目标时构造 kind 1、
参数 `(0, 0xFFFF)`；有目标时构造 kind 11、参数 `(slot & 0xF, profile)`，
并立即镜像到 `+3231/+3232/+3234`。kind 11 的坐标解析按玩家 `+2010`
地面编号选择原生地面点，再旋转局部偏移得到目标参考点：

| profile | 局部偏移 `(x, y, z)` |
| --- | --- |
| 0 | `(0, 500, 1000)` |
| 1 | `(0, 400, 800)` |
| 2 | `(0, 400, 1500)` |
| 3 | `(0, 600, 600)` |

这些是四个数值档案，不代表已证明的招式或站位名称；也不同于仅把玩家位置
绑定为 kind 1 的 `0x13`。证据为 `0x108538B0` case 11 与参数生产者 `0x10864640`。

`0x3F`（`0x10863B20`）按大端区域 ID 选择地面移动记录，最后一个载荷字节
乘以 10 用作探测高度，不是距离半径。成功时保存后续指令到 `+2648`，设置
kind 9 的移动记录参数并转入 `root[12]`；`FF 04/05/06` 推进或放置记录，完成后
恢复续行。`FF 04/05` 共享入口，但后续 `0x10867B06` 仅在 selector 4 且
保存的 kind 为 9 时执行区域/位置落点，selector 5 不走此落点分支；`FF 06`
在保存 kind 为 9 时直接进入放置路径。因此三种收尾不能视作相同编码别名。
`0x3F` 同时配置移动上下文和转移脚本游标，不能仅描述为选最近目标。

## 0x94 全局 AI 分支选择值

`0x108682B0` 读取共享全局 `0x11C6A7E8`，不读取怪物的 `+2680` 模式字节。
规范布局为 `94 00 <count>`、若干 `94 01 <u8 value>` 分支、可选
`94 02` 默认分支和 `94 03` 结束标记。比较使用有符号 i32 全局值与零扩展的
u8 case；相等进入正文，全局值小于 case 时停止查找并扫描至默认分支或结束。

已核对的 15 个静态脚本都含两个 case：`0` 进入通常的条件／子脚本选择，
`1` 只执行 `82 03 04`，即调用当前根表的 `root[18][4]`，没有默认分支。
该槽位的含义取决于根表，不能把全局值 `1` 命名为某个通用招式：

| 根表示例 | case 1 的目标 | 目标脚本 |
| --- | --- | --- |
| 火龙 `0x11A3EDD0`、`0x11A3E220` | `0x11847608` | `05 03 02 00 FF 02`：`self.action(3:2, 0)` 后返回 |
| 岩龙 `0x11A13C68` | `0x11779574` | `13 05 03 04 00 FF 02`：绑定当前目标后执行 `self.action(3:4, 0)` |
| 铠龙系 `0x11A17268`、`0x11A17418`、`0x11A176F0` | `0x117A6004`、`0x117A6810`、`0x117A782C` | 同样为 `13 05 03 04 00 FF 02` |
| 刻龙 `0x11A3EE30`、`0x11A3E2A8` | `0x11833B74` | 仅 `FF 02`，不执行动作 |

对应的 0x94 脚本位于 `0x1177932C`、`0x117A5648`、`0x117A65C0`、
`0x117A6CA0`、`0x11848460`、`0x118492D8`、`0x1184AD20`、`0x1184C7F0`、
`0x1184E278`、`0x1184FCA8`、`0x11850EC8`、`0x11852118`、`0x118539A8`、
`0x11854D88`、`0x11978760`。表中物种关系来自地图 `0..97`、静态物种槽
`0..131` 的根表目录；不代表同一物种在所有地图使用同一个根表。

### 设置来源与地址隔离

当前 DLL 的直接引用为初始化清零 `0x108603E9` 和读取 `0x10868303`。
初始化函数在 `0x10860369` 执行 `xor ebx, ebx`，再以 EBX 写入该全局；
它由 actor 初始化路径 `0x1086EAD0` 的 `0x1086EB51` 调用，而非仅在程序启动时执行。
变量位于 PE 节的零填充虚拟尾部，没有磁盘中的非零配置初值。其内部字节
`+1..+3` 也没有单独的直接引用；全局地址没有作为数据指针出现在文件中。

相邻存储的已确认边界：

- 前方 `0x11C6A7C8..0x11C6A7E7` 属于 `0x10837DC0` 的 UI 矩形；
  索引被限制在三个 8 字节条目内，额外的矩形也只占 `+E0..+E7`。
  `0x108F29B0` 按调用方给定的条目数读取矩形，不向其后方写入。
- 更前方的 `0x11C6A60C` 是六个 dword 的位集。`0x10836340` 的索引写入
  检查下标 `<= 5`，不会延伸至该选择值；`0x11C6A624` 是另一个计数字段。
- 后方 `0x11C6A7F0` 是三个 16 字节的事件回调记录，初始化函数为
  `0x1087ECB0`、`0x1087F110`，调度函数为 `0x1087F710`。
  其描述目录 `0x11A46130..0x11A465B0` 的 48 个条目包含 14 个不同回调。
  这些回调及其记录指针转发路径没有向记录头之前的负偏移写入；
  `0x1087FFB0`、`0x10880180` 等共享处理函数也不是该选择值的设置方。
  邻接的 `0x11C6A7EC` 事件状态不能当作 `0x11C6A7E8` 的别名。

同一组样本中的 `mhfo.dll` 的对应处理函数为 `0x1084D810`，读取全局 `0x11C12C30`。
其 201 字节函数体与 HD 版仅全局地址操作数不同；地址字面量仍只有
`0x10845949` 的初始化写入和 `0x1084D863` 的读取，对应 RVA 字面量没有命中。
两版导出表均不导出该变量。同组游戏文件中的 `mhf.exe`、`mhfi.exe`、`mhl.dll`、
`mhf-zz.exe`、`hello.exe`、`gdiplus.dll`、`ogg.dll`、`vorbis.dll` 未包含
这两个变量的 32 位 VA 或 RVA 字面量。这些文件检查不能排除运行时地址计算、
未检查模块、外部工具或注入代码的写入。

非零值写入路径尚未确认。因此可确认其在上述脚本中选择“常规 AI／预设分支”，
但是否为测试或调试开关仍未证实，也不能由直接引用数断言它永远为零。
DSL 以约定名称 `match context.debug_mode` 表达完整有序的数值分支，
不提供设置操作，也不把调试用途视为已证实的原生语义。非规范布局保留 `native(...)`。

## 昼夜分支（0x77）

`0x1ED6BCA0` 的 `0x08` 为昼标志，`0x10` 为夜标志。
`0x108665F0` 的 selector 0 在 `(flags & 8) != 0 || (flags & 0x10) == 0`
时进入正文，仅夜标志设置而昼标志未设置时跳至 else 或结束。
selector 1 为 else，selector 2 为结束。两位均清除或均设置时都进入正文，
因此完整语义不能缩减成单独读取昼标志。

写入与独立消费者证据：

- `0x106EF910` 根据全局时间值 `0x1EE24964` 与 `0xA8C0`（43200）的比较，
  清除这两位后分别设置 `0x08`（小于）或 `0x10`（大于等于），并保存昼夜索引到 `0x1ED52840`。
- `0x107160F0` 检测该时间侧相对已保存索引发生变化时，按同一个比较结果从
  `0x11879958` 的两个 4 字节记录选择音频 ID：索引 0 为 169，索引 1 为 168。
- 音频初始化 `0x114DC510` 设置音乐表基址 `0x115F99C8`；
  `0x114DC310` 以 `16 * ID` 索引文件名。169 对应 `ef_c_n_d.mus`（夜转昼），
  168 对应 `ef_c_d_n.mus`（昼转夜），与昼夜方向相互印证。

该指令读取环境标志，不直接读取时钟，不改变昼夜，也不是倒计时条件。
DSL 使用 `if context.is_daytime`；完整可无损往返的条件结构恢复为 if/else，
非规范布局保留 `native(...)`。

### 0x2E 感知参数档案（actor+1968，2026-10 静态复核）

`0x1084FB80` 把 `actor+1968` 指向「物种感知参数表」的第 `n` 条记录，
`n` 来自 `2E` 操作数：`v14 = sub_108471C0(actor)[3]`（即物种表 `+12`），
然后 `*(actor+1968) = &v14[32 * n]`，**没有范围检查**。
原生还会按物种与运行条件改写 `n`：物种 1 在 `sub_1087CDE0` 成立时改为 2，
`0x41`/`0x64` 改为 2/3，`0x77`/`0x78` 改为 4 或 2，`0x7B` 为 `n+2`，
`0x55`/`0x5F` 在区域 124 时为 2。

记录为 32 字节，已确认字段：

| 偏移 | 含义 | 证据 |
| --- | --- | --- |
| `+0` | 最大距离：槽位距离大于它则剔除 | `0x1084F7C0` |
| `+4` | 最小距离：大于槽位距离则剔除；各档案实测均为 `0` | `0x1084F7C0` |
| `+8` | 允许高于自身的高度：目标高出超过它则剔除 | `0x1084F7C0` |
| `+12` | 允许低于自身的高度：目标低于超过它则剔除 | `0x1084F7C0` |
| `+16` | 半视角 `u16`（`1/65536` 圈），与目标夹角差按环绕比较 | `0x1084F7C0` |
| `+24` | 附加距离阈值（另有消费者用作上限） | `0x108507C0` |
| `+28` | 附加距离阈值：槽位距离小于它时置 `+2687`/`+2820` 位 | `0x10854D80` |

`0x1084F7C0` 与 `0x10854D80` 都由每帧更新 `sub_108728A0` 调用，
它们对玩家数组的四个槽位更新发现位 `+2684` 与追踪位 `+2687`，
所以这组参数就是 `0x4A` 一节所述「配置的距离、高差、角度检查」的来源。
实测物种表中的档案数并不固定：主区共 113 条记录、59 种不同组合；
按物种表指针到下一个不同指针的距离统计，176 个物种中
2 条×60、6 条×49、1 条×23、4 条×14、3 条×14、5 条×4，另有 12 个物种的表在别处。
角度值只落在 `10°`、`20°`、`30°`、`40°`、`45°`、`60°`、`80°`、`90°`、
`100°`、`110°`、`120°`、`135°`、`140°`、`160°`、`180°`。
因此下标是物种私有索引，不是共享枚举；DSL 语句为 `self.select_perception_profile(n)`。

### 0x2D 提交扫描到的地面物件（2026-10 静态复核）

`0x10869A6A`（1 字节内联处理）把 `actor+2581 = 7`（目标类型 7），
`+2582 = +2922`、`+2584 = +2923`。另外的字节 `+2921` 不进入动作元组，只作为记录的一部分。
DSL 语句为 `self.bind_scanned_object()`；它只提交目标上下文，不筛选、不移动、不播放动作。

记录来源是全局 32 槽地面物件表 `dword_1ED8BE80`（计数 `byte_1ECB17F4`，
由 `sub_1141F790` 登记/注销；对象的 `+3` 子类型由 `sub_1141E910` 分发，`case 3` 登记）。
条目字段：`+0/+4/+8` 世界坐标、`+0x0C` 自身可感知距离、`+0x10/+0x11/+0x12` 身份三元组、
`+0x13` 已消耗标记、`+0x18` 所属区域 ID。

两个记录者都先清空记录（`+2922 = 0xFFFF`、`+2921 = 0xFF`）：

| 记录者 | 条件 | 调用者 |
| --- | --- | --- |
| `sub_10850880` | 同区域、距离小于 `entry+0x0C`、过遮挡测试 `sub_108D0360` | 每帧更新 `sub_108728A0` |
| `sub_10850A00` | 同区域、同高度（高度差在容差内）、`entry+0x13 == 0`、取最近且可选距离上限 | 物种动作代码（`0x110`/`0x111` 段） |

命中时写入 `+2922 = entry+0x10`、`+2923 = entry+0x11`、`+2921 = entry+0x12`；
未命中保持清空值，所以 `0x2D` 提交的也可能是“未找到”。
`sub_10850B40` 按 (`+0x10`, `+0x11`) 反查条目；`sub_1085BFE0` 消费条目
（置 `entry+0x13 = 1`）并清空记录。

原生动作处理器做同一件事：`sub_10850B80` 先设 `+2581 = 7` 并写入组／参数，
随后调用解析器 `sub_108538B0`（目标类型 7 的 `case 7` 会按这对字节找条目并用其位置）。
它有 17 个调用点，都是物种动作函数（火龙 `0x10BE5EC0` 等），
所以“记录物件目标”是通用机制，`bait_detected` 只是其中一个用途。

目标类型 7 解析出的坐标来自条目自身位置；具体物件类别（运搬物、设置物或其他）
尚未确认，不要写成“肉饵”或“蛋”。

确认的字段可以按用途描述，未确认的类别和枚举继续按地址记录。该清单的机器可读形式是 `opcodes-*.json` 记录里的

## 已解决 / 待定项

- `+1826` 已定：它是解释器记录上的 `u8` 目标下标（`0xFF` = 无）。与之竞争
  的 `void*` 读法来自 `0x7F` 的 handler `0x10866770`，它的第一个参数是字节码
  游标（`cursor+1`），不是记录的字段——分派处以 `lea eax, [edi+1]` 装入它。
- `+2612`/`+1826` 不是无条件指向玩家下标：它们按已提交的命令 kind 解析到两个
  不同数组（`1`/`11` → `byte_1DC6B750`，`13` → `dword_1ED7AD2C`）。玩家域
  路径（`0x10864A30` + 仇恨表 + `FF F7` 的 `NOT_FOUND_PL`）已证明；kind 13
  路径可以选择同区域（`+2040` 相等）的另一只怪物；`06 0D` 的四种子模式
  还分别限制大型、存活、不同物种及原生资格。`0x58` 则把原生配对首领已提交的
  玩家目标复制出来。两者不能因为都读取 actor 数组就合并成同一种配对机制。
- "关联 actor 指针"这个描述附着在多个不同字段上（`0x27` 的 `+27`、`0x47` 的
  `+2729`、`0x3B`/`0x3C`/`0x44`/`0x58` 的 `+3172`、
  `0x59` 的 `+3200`、`0x83` 的 `+1112`）。只有 `+3172` 有
  `domain_notes` 级证据（`sub_108578A0` 扫描 `dword_1ED7AD2C`）；其余保持
  `generic`，不得并入同一个名字。`+3185` 已确认为区域移动路线配置编号，
  也不属于关联 actor 指针。

### 0x4A 当前目标发现标志（2026-09-25 静态复核）

在 `mhfo-hd.dll`（SHA-256 `95c580195f4080d2e9582c8c9df36abeb280476e088b6366583c5f138da8f301`）中，
`0x108646B0` 的选择子 0 检查 `target != 0xFF && (u8(1 << (target & 0xF)) & actor[2684]) != 0`，
其中 `target = actor[2612]`。成立则继续正文，否则跳到同层 `4A 01` 或 `4A 02`；选择子 1 跳过 else 到结束。
这里返回的是下一条脚本指针，不是从 AI 子脚本返回。

`0x1084F7C0` 遍历玩家数组 `0x1DC6B750` 的四个槽位，根据有效性、区域及配置的距离、
高差、角度和遮挡检查更新发现位。`0x10854B90` / `0x10854BF0` 也可在基本有效性、
存活和同区域检查通过后强制置位，没有重复整套视野检查。
`0x10854C70` 在发现位存在时设置 `+2687` 并刷新 `+2688 + 2*i`；发现位消失后，
后两者可继续保留至计时到期。因此“当前目标的发现标志”比“当前有仇恨”或“视线无遮挡”准确。
`0x4A` 本身不验证目标域，也不重新执行检测；上述玩家含义来自发现位的生产者。
以上为 IDA 静态证据，未作实机观测；DSL 条件为 `self.target_detected`。
