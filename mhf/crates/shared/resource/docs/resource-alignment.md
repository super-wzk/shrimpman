# 资源寻址基准与打包布局

本文说明资源偏移的寻址基准、容器填充规则和工作台的重打包行为。
布局规则依据原生读取代码与已识别的资源结构，文件布局回归不能替代游戏内兼容性验证。

## 证据与适用范围

必须区分三件事：偏移字段从哪里寻址、原包如何安排填充、原生读取器是否强制对齐。
例如 MHA 的成员 offset 相对整个 ABN 起点，不是相对 `+24`；只有成员排列的格点
相对 `+24`。满足同一模数也不代表存在可以自由增减的 padding。

容器应先通过 `mhf-resource` 的 ECD/EXF/JKR 解码器打开编码层，再校验目录及成员。
无签名的 offset/size 目录可能与其他数值表同形，识别时还需验证成员内容。
事件相机数组的布局验证使用 `EventCamera::parse` 后独立检查边界，
不能只用要求 16 字节布局的 probe 证明对齐规则。

下文原生地址按 `mhfo-hd.dll` 的映像基址 `0x10000000` 记录。
不同客户端版本可能改变入口地址和资源布局，适配时需重新核对对应读取路径。

## 容器规则

`align_up(x, a)` 表示向上取到 `a` 的整数倍，已经对齐时不增加。
除 MHA 的排列格点外，下表的起点均指当前解码后的容器自身起点，不能继承父容器基准。

| 容器或区域 | 寻址基准 | 实样打包规则 | 原生证据与限制 |
| --- | --- | --- | --- |
| MHA 成员 | ABN 起点 `0` | `(offset - 24) % 512 == 0`；`padded_size = align_up(size + 24, 512)` | 原生加载链按 offset/size 读取，不使用 padded_size 定位；该路径没有强制 512 对齐 |
| MHA 名称区、目录表 | ABN 起点 `0`；name_offset 单独相对名称区 | 名称区紧接全部成员分配区；目录表紧接名称区，没有另外对齐 | 目录表起点可以不是 4 的倍数，不可给整个 MHA 套用统一对齐 |
| 普通模型 offset/size 目录 | 当前模型包起点 `0` | 已识别武器包连续紧排，可有奇数或非 4 倍数偏移 | 模型读取器直接 base + offset |
| TXB | 当前 TXB 起点 `0` | 已识别图片目录采用紧排布局 | 成员起点可以是奇数；原生按字节偏移交给贴图加载器 |
| MOMO | MOMO 签名起点 `0`，不是 count 字段或目录末尾 | 每项起点 `align_up(previous_end, 64)`；首项从目录末尾计算，文件尾也补到 64；填充全零 | 这是已识别的打包布局，是否为原生读取的硬要求尚未确认 |
| StageArchive | 当前 StageArchive 起点 `0` | 已识别布局的成员起点为 16 倍数，间隙全零；可以包含超过最小需要的填充 | 已确认的固定成员和追加成员读取直接 base + offset；总长度不一定为 16 倍数 |
| ObjectPackage，紧排实例 | 当前对象包起点 `0` | 成员连续排列，无头后／成员间／尾部填充 | 不能因父级是 Stage 就追加 16 对齐 |
| ObjectPackage，16 布局实例 | 当前对象包起点 `0` | 成员起点按 16 向上对齐；填充全零，最后一项后不额外补齐 | 对象包读取直接使用 offset；两种生产布局的选择条件尚未确认 |
| EffectArchive | 当前特效包起点 `0` | 已识别特效目录采用紧排布局 | 4 的倍数来自成员长度与目录宽度，不能据此增加 padding |
| 事件相机数组 | 当前相机成员起点 `0` | 32 字节头后四数组依次按 16 对齐，成员末尾也补到 16 | 原生直接重定位四个偏移，没有取整 |

### MHA：分配长度不等于最小向上取整

已识别的 MHA 分配布局满足上述 `size + 24` 公式，分配区按物理位置连续排列，
填充全部为零。该布局中 `size == 0` 的成员仍各占 512 字节，不能当作没有布局占用。

该规则使尾部填充范围为 24..535 字节，与 `align_up(size, 512)` 不等价。
例如 `wd000snd.abn` 的第 1 项 `size=30720`，但 `padded_size=31232`。
`+24` 的打包器语义尚未确认，
不应把它误称为每个成员自带的 24 字节头。

以外部存储长度为 31893、分配长度为 32256 的 `wi521.bin` 为例：
若将成员替换为 23692 字节，新分配长度应为 `align_up(23692 + 24, 512) = 24064`。
这与简单取整在本例恰好相同，但两种公式不能推广为等价。

### 同一父容器内也能混用布局

`stage/st002.pac` 的成员 31 是 StageArchive。其两个子对象包分别为：

```text
/31/3：目录末尾 44；成员 offset = [44, 52, 180388, 180756, 778720]
       连续紧排。
/31/6：目录末尾 52；成员 offset = [64, 80, 3488, 3616, 3648, 4352]
       相对当前对象包按 16 对齐。
```

Stage 的成员间隙可以比最小 16 字节对齐所需填充多出整块空间。
空固定槽与额外块存在关联，但完整生成算法尚未确认。
例如 `stage/st133.pac/31` 的成员 0 位于 80、长度 256；固定槽 1、2 为空，
首个追加成员位于 368，中间保留 32 字节。不能只按非空项重排并最小化所有零间隙。

`stage/st001.pac/31` 总长度 1509462，非 16 倍数；不能从成员起点对齐推导文件尾也对齐。

### 原始 wi521 内部没有统一 4 字节对齐

ECD 解密后的普通模型包如下，三个成员首尾相接：

| 槽 | offset | size | 内容 |
| --- | ---: | ---: | --- |
| 0 | 28 | 19550 | JKR → FMOD，解码后 70656 字节 |
| 1 | 19578 | 108 | JKR → FSKL，解码后 1100 字节 |
| 2 | 19686 | 12191 | TXB |

槽 1、2 的起点除以 4 均余 2。这些是压缩成员的存储偏移，不是解码后 FMOD/FSKL
内部结构的位置。图片目录也有直接反例：解密后的 `campaign/x04.txb` 成员偏移为
`[28, 103317, 103413]`，长度为 `[103289, 96, 96]`，没有间隙。

### MOMO 的边界与文件尾

`sound/grdn_fes.snd` 总长 600192，目录结束于 32：

```text
offset = [64, 3136, 598656]
size   = [3018, 595514, 1504]
```

首项、后续两项和最终文件尾均按 MOMO 自身起点补到 64，最后一项后有 32 字节零填充。

## 编码层与内部结构

| 结构 | 基准和步进 | 对齐设计边界 |
| --- | --- | --- |
| ECD | payload 固定从当前 ECD `+16` 开始，以头内长度限定 | 字节加密和 CRC 不要求统一块长；外部未知尾部不能视为可删除填充 |
| EXF | 从当前 EXF `+16` 到文件末尾 | 编码处理字节流，不等于容器填充；不据此推断解码后资源的布局 |
| JKR | payload 从当前头的 `data_offset` 开始；解码后成为新的资源起点 | 固定头长 16，头扩展由 data_offset 控制，不能硬编码 payload 起点为 16；压缩长度与解码长度不能混用 |
| FMOD/FSKL block | 当前 block 的 header 长 12；下一 block 为当前起点加声明 size | 未见额外 align_up；size 含头和未识别尾部，不能统一删除尾部或补到 16 |
| MOT offsets 表 | 解码 MOT 起点；原生对 group.offsets_offset 做有符号 /4 再乘 4 | 有效非负偏移等价于忽略低两位；是寻址编码，不是尾部填充规则。motion 本体仍直接 base + offset |
| MOT clip/track/channel | clip 头 20，track/channel 头 12；按各自 byte_size 前进 | 变长需要更新层级长度、目录引用、别名与空槽；目录 probe 的 8 倍数条件不是全局对齐规则 |
| 独立 grouped material | legacy 从 0 开始；extended 先跳过 1 字节 marker，再连续读结构 | extended 首记录在资源相对 `0x21`，不能为 u32/f32 字段自动补到 4 |
| PNG | 签名长 8；chunk 逐个按 `12 + data_length` 前进 | IHDR 后下一 chunk 在 `0x21`，不做 chunk 对齐；修改涉及长度和 CRC |
| DDS | 普通头后数据在 128，DX10 在 148；后续按像素格式、mip、pitch 计算 | 图像 row pitch 与压缩块约束不是外层归档对齐；此处仅说明解析器的寻址方式 |
| DAT | 解码 DAT image 起点；不同表按各自 stride 读取 | 表起点的对齐不能推广为逐记录对齐，例如 DAT[160] stride=18，不能逐记录补到 4 |

## 原生读取证据

以下读取入口说明各资源的寻址方式，客户端版本适用范围见前文。

| 地址 | 消费方式 |
| --- | --- |
| `1158BB30` | 读取 MHA 24 字节头，按头 `+4` 的偏移读取 count×20 目录；按 `+12/+16` 读取名称区 |
| `1158C300` | 按有符号低 16 位 ID 定位槽，将 entry `+4/+8` 写入 offset/size 表；重复 ID 后项覆盖，entry `+12` padded_size 未进入该表 |
| `1158CB60 / 1158C420` | 文件名数字 ID 按声明范围查找；offset 为零表示未找到，size 为零不读取 |
| `1158C4D2 / 1158C508` | 同步读取：offset 原样交给 SetFilePointer，实际 size 交给 ReadFile |
| `1158C696 / 1158C6B1` | 异步读取：offset 写入 OVERLAPPED.Offset，按实际 size 读取 |
| `108DF4B0 / 108DF570` | 模型包成员直接 base + offset，再按 size 拷贝或 JKR 解码 |
| `108DF7D0` | TXB 的 base + offset 和 size 原样交给贴图加载器 |
| `113E8DA0` | Stage 固定 #0、#2 及追加项直接 base + offset；该函数未覆盖固定 #1 |
| `113DA650 / 113DA8CC` | 对象包直接按自身 base + offset 读成员；共享引用先定位 Stage 内对象包，再使用该包自身基准 |
| `10829E70` | 相机的 `+10/+14/+18/+1C` 四个数组偏移直接加相机基准，不取整 |
| `108FD285..108FD295` | MOT offsets 表的偏移做 signed /4，再按 DWORD 索引寻址；motion 本体在 `108FD2A1` 直接相加 |
| `100022A0 / 10002630` | FSKL/FMOD 遍历下一 chunk 时直接加 chunk 的 `+8` 声明长度 |

MHA 头 `+0x14/+0x16` 分别命名为 `first_file_id: i16` 和 `file_id_count: u16`，
用于资源 ID 索引，不参与对齐。原生按无符号槽数分配空间，但按有符号槽数判断索引，
有效范围为 `0..=32767`。entry 的 file_id 低 16 位按有符号值减去起始 ID，
高 16 位保留原值。`MhaArchive::file_id_index()` 单独验证范围并建立原目录项映射，
重复 ID 保留最后一次写入，未分配槽与显式空项保持区别。工作台将该映射按需展开为
只读派生字段，真实成员顺序不变；头字段与 ID 的修改继续使用原有 Typed Binding。
这些索引规则与 `padded_size` 的分配布局分别验证。

## 布局约束

1. 将偏移引用的基准、成员排列的基准、分配长度规则和文件尾规则分别声明。
   MHA 的 `+24 / 512` 格点、`size + 24` 分配公式及不对齐的名称／目录区不能由单个模数概括。
2. 规则归属具体容器实例，不自动传给子资源。ObjectPackage 已确认混用紧排和 16 布局，
   其选择条件仍需确认；不能只凭 Kind 或碰巧可整除就宣布某规则。
3. 只有格式确认的可调填充才能重新生成；空槽的分配区、Stage 额外间隙和未知 block 尾部
   都不能因全零就删除。字段展示可以暴露 padding，但布局与重定位应由容器规则负责。
4. 连续紧排与显式偏移均是正常布局。缺少 align_up 不自动构成打包错误，
   重打包后的兼容性仍需通过对应原生加载入口验证。

相关解析实现见 [container.rs](../src/container.rs)、[event_camera.rs](../src/event_camera.rs)、
[motion.rs](../src/motion.rs)，其他布局说明见 [容器格式](container-formats.md)、
[场景格式](stage-formats.md)、[模型格式](model-formats.md)、[材质参数](material-parameters.md)。

## 重打包实现与验证

工作台在每个物理容器的批量替换开始时，根据完整目录、分配范围和填充字节确定布局；
规则定义见 [repack/layout.rs](../../../mods/workbench/src/edit/repack/layout.rs)，
重定位见 [repack.rs](../../../mods/workbench/src/edit/repack.rs)。不同容器各自选择规则，
不使用 Rust 的内存对齐，也不将父容器对齐传给子资源。

- MHA 完整匹配已确认分配布局时，替换整个旧分配区，以 `align_up(size + 24, 512)`
  重建零填充。目录／名称区和后继成员按分配长度差移动；有分配区的空成员也移动，
  无分配区的空槽保留其陈旧偏移。
- MOMO 完整匹配最小 64 字节零填充布局时，重算成员间及文件末尾填充。
- Stage 匹配起点 16 对齐及零间隙时，只重算最小填充，额外整块间隙保持；
  最后一个成员后原有尾部原样保留，不额外创建文件尾对齐。
- ObjectPackage 只有完整匹配最小 16 字节布局才调整填充。普通 offset/size 目录头
  结束于 `4 + 8*count`，不可能是 16 的倍数，因此头后间隙可以区分这类实例与紧排实例。
- 普通目录、TXB、EffectArchive 和未匹配上述完整规则的布局维持原有字节间隙，
  不根据单个偏移的可整除性猜测对齐。声明的分配区或实际替换区若与其他成员或元数据
  重叠，则拒绝变长替换；分配范围不同的别名也拒绝处理。

每批按物理位置从后往前替换，布局策略固定，但每次重新读取已移动的目录。
每步输出除重新解析外，还验证所选布局。FMOD/FSKL/MOT/相机等内部结构不支持
变长序列化；等长字段编辑保持内部容量，编码层长度变化交给所属容器重排。

合成回归覆盖跨分配边界、别名、两类空槽、清空最后成员、额外间隙、元数据重叠、
批量原始范围及嵌套 JKR/MOMO/MHA 编辑。可选的原始资源回归遍历 MHA 包，
检查非空成员、空分配槽、别名及元数据，并覆盖 MOMO、Stage 和两种对象包布局。
游戏文件不写回；可分别运行普通与实样回归：

```sh
cargo test --manifest-path mhf/Cargo.toml -p mhf-workbench --target aarch64-apple-darwin
MHF_RESOURCE_GAME_ROOT=/path/to/game cargo test --manifest-path mhf/Cargo.toml \
  -p mhf-workbench --target aarch64-apple-darwin alignment_native_tests -- --ignored --nocapture
```

工作台不自动规范化已经失去原包布局的重定向文件。应使用未损坏的原始资源，
执行替换后再打包，并在目标客户端验证效果。
